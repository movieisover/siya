## 0. 먼저 — 1단계 회신의 사실 정정 하나

1단계 회신에서 ①의 채택 근거로 **"추가 API 호출 없이 기존 조회 응답에서 뽑을 수 있다"**고
적었는데, **이건 틀렸다.** 구현 전에 실측해서 확인했다.

| daily_update 기존 호출 | tr_id | 상태 플래그 포함 |
|---|---|---|
| Step 1 일봉 | `FHKST03010100` | **없음** (output1 30개 키 전부 시세·밸류) |
| Step 4 수급 | `FHKST01010900` | **없음** (output 22개 키) |
| 상태 조회 | `FHKST01010100` | 있음 ← **별도 엔드포인트** |

상태 플래그는 **주식현재가(`inquire-price`) 전용**이라 종목당 1콜이 따로 든다.

**비용 재산정**: 전종목 2,773 × 0.4s ≈ **19분 추가**. 현재 `daily_update` 런이 ~126분이니
약 145분이 된다. 워크플로 `timeout-minutes: 210` 안에 여유 있게 들어가고, 레포가 Public이라
Actions 분 단위 과금도 없다. **결론적으로 ①의 채택 판단은 그대로 유효하다** — 비용이
"0"이 아니라 "19분"으로 바뀌었을 뿐이다. 다만 근거로 인용한 문장이 틀렸으니 정정한다.

## 2. 스키마 — 답변서 §6 세 가지 요구를 그대로 반영

```sql
CREATE TABLE stock_status (
    stock_code          VARCHAR(10) NOT NULL REFERENCES stocks(stock_code),
    snapshot_date       DATE NOT NULL,        -- 관측일

    iscd_stat_cls_code  VARCHAR(4),  -- 00그외 51관리 52투자위험 53투자경고
                                     -- 54투자주의 55신용가능 57증거금100% 58거래정지 59단기과열
    mang_issu_cls_code  VARCHAR(4),  -- 관리종목 Y/N
    mrkt_warn_cls_code  VARCHAR(4),  -- 00없음 01주의 02경고 03위험
    sltr_yn             VARCHAR(4),  -- 정리매매 Y/N
    short_over_yn       VARCHAR(4),  -- 단기과열 Y/N

    source              VARCHAR(20) DEFAULT 'kis_api',
    observed_at         TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (stock_code, snapshot_date)
);
```

- **"배제 여부를 시야가 판정하지 말 것"** → 판정 컬럼(`is_excluded` 등)을 **두지 않았다.**
  코드에 `is_notable()`/`describe()` 헬퍼가 있지만 **로그 출력 전용이고 DB에 저장하지 않는다.**
  판정 규칙이 그쪽에서 바뀌어도 시야를 건드릴 일이 없다.
- **"KIS 원값 그대로, 문자열로 풀지 말 것"** → `'51'`/`'58'`/`'Y'`/`'02'` 그대로. 빈 문자열만
  `NULL`로 정규화했다.
- **"스냅샷 이력이 쌓이는 구조"** → PK가 `(stock_code, snapshot_date)`라 날짜별로 행이
  쌓인다. 같은 날 재실행하면 그 날짜 행만 갱신되고 과거 날짜는 보존된다.

### ③ 투자경고도 같이 넣었다 (범위 확인)

`mrkt_warn_cls_code`는 우선순위 ③이지만 **동일 응답의 필드라 한계비용이 0**이고, 답변서에서
"배제 판정 하지 말고 값만 그대로 실어 달라"고 한 요구가 이 테이블의 설계 원칙과 정확히
같다. 나중에 마이그레이션을 한 번 더 하는 것보다 지금 컬럼을 두는 게 낫다고 판단해 포함했다.
`sltr_yn`(정리매매)도 같은 이유로 넣었다 — 답변서 §1에서 체결 게이트 항목으로 든 것이다.

**②(투자주의환기, KIND)와 ④(계속기업, DART)는 손대지 않았다.** 별도 소스라 이 작업과 섞이지
않는다.

### 조회 예

```sql
-- 최신 스냅샷 전종목
SELECT DISTINCT ON (stock_code) *
  FROM stock_status ORDER BY stock_code, snapshot_date DESC;

-- 체결 게이트 (살 수 있는가)
WHERE iscd_stat_cls_code = '58' OR sltr_yn = 'Y'

-- 팩터 배제 게이트 (부실한가)
WHERE mang_issu_cls_code = 'Y'
```

플래그 선 종목만 빠르게 뽑도록 부분 인덱스를 걸어뒀다(전종목의 ~2%).

정리매매 3종목은 전부 관리종목이기도 하다: 알에프세미(096610) · 시스웍(269620) ·

### 1단계 측정치 재현 확인 ✅

| | 관리종목 | 거래정지 | 거래정지인데 관리종목 아님 |
|---|---|---|---|
| 684 유동성통과 | 5 | 5 | **002780 · 002880 · 062970** |
| 313 F게이트 | 2 | 1 | – |

1단계 실측(8/27 오전, KIS 단건 조회)과 **완전 일치**. 파이프라인을 타고 DB에 들어간 뒤에도
같은 숫자가 나온다.

### 네이버 교차검증 — 차이 3건 전부 규명됨

DB `mang=Y` 166 vs 네이버 관리종목 목록 167. 차이는 **불일치가 아니라 범위 차이**였다.

- **네이버에만 2건** — `373790`, `454180`: 둘 다 **KIWOOM ETF**다. 네이버 관리종목 페이지는
  ETF를 포함하지만 시야 `stocks`는 KOSPI/KOSDAQ 보통주만 담는다. **범위 밖.**
- **DB에만 1건** — `269620` **시스웍**: KIS는 `mang=Y, stat=51, sltr=Y`(정리매매)로 잡는데
  네이버 목록에는 없다. **KIS 쪽이 더 완전하다** — 정리매매 단계 종목을 놓치지 않는다.

즉 실제로 겹치는 모든 종목에서 두 소스가 일치하고, KIS가 커버리지가 더 넓다. **1단계에서
KIS를 권한 판단이 데이터로 확인됐다.**

### `00 그외` 35건에 대하여

`iscd_stat_cls_code='00'`이면서 `mrkt_warn_cls_code`가 NULL인 35종목이 있다(두 집합이 정확히
일치). 현대홈쇼핑·신세계푸드·코오롱ENP 등 **정상 보통주**이고 우선주는 0건이다.
`00`은 KIS가 정의한 정상값("그외")이지 결측이 아니다. **플래그가 선 종목이 아니므로 배제
로직에 영향 없다.**

## 6. 실패 처리 방침 — 한 가지 알아둘 것

Step 6은 FX(Step 5)와 같이 `try/except`로 격리했다. **실패해도 Step 1~5(시세·PER/PBR·
수급)를 막지 않는다.** 대신 그 날 스냅샷은 비고, **과거 상태는 어느 소스로도 소급 복원이
안 되므로 그 날은 영구히 빈 칸으로 남는다.**

`replay.py`에 이 게이트를 적용하지 않기로 한 결정과 같은 이유이고, 나중에 이력을 쓸 때
"연속된 날짜가 아닐 수 있다"는 전제로 읽어 달라. 빠진 날은 직전 스냅샷을 끌어 쓰는 게
현실적이다.
